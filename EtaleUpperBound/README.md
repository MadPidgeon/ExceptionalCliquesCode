# EtaleUpperBound

Given a prime p and a finite étale algebra $A$ over the finite field $\mathbb{F}_p$, "EtaleUpperBound" computes the clique number of $A$, where elements in the clique are supposed to satisfy $N(x-y)=\pm1$, where $N$ denotes the norm from $A$ to $\mathbb{F}_p$.

The algebra is defined by 

$`A=\mathbb{F}_{p^{d_1}}\times...\times\mathbb{F}_{p^{d_r}}`$, 

where $d_1,...,d_r$ are the integers given as input.

The program relies on clique search in graphs where vertices represent elements of $A$ and edges are $`\{x,y\}`$ such that $N(x-y)=\pm1$.

The implementation uses [PARI/GP](https://pari.math.u-bordeaux.fr/) for finite-field arithmetic and calls [Cliquer 1.21](https://users.aalto.fi/~pat/cliquer.html) directly for exact maximum-clique computations.


## Main ideas

Every clique is normalized to contain 0 and 1. The remaining normalized vertices belong to the set of exceptional units 

$`E=\{x\in A \mid N(x)=\pm1, N(1-x)=\pm1\}`$.

The program then:

1. indexes the group $`H=\{x\in A \mid N(x)=\pm1\}`$ directly, rather than indexing the complete unit group;
2. enumerates the exceptional set $E$;
3. partitions $E$ into orbits under the six Möbius symmetries generated by $x\mapsto 1-x$ and $x\mapsto1/x$, the local Frobenius actions on each coordinate, and permutations of equal-degree factors;
4. constructs one canonical local graph for each remaining symmetry orbit;
5. computes its exact clique number with Cliquer.

### Implementation of the main ideas

#### 1. Direct indexing of H

For the i-th factor, let

$q_i=p^{d_i}$,   $n_i=q_i-1$,   $h=(p-1)/2$.

First fix a primitive generator $`\zeta`$ of $`\mathbb{F}_p^*`$. For each distinct field
$`\mathbb{F}_{q_i}`$, PARI returns a primitive generator. The program replaces it, if
necessary, by another primitive generator $g_i$ having the normalized norm

$`N(g_i)=\zeta`$.

Concretely, if PARI initially gives a primitive generator g with

$`N(g)=\zeta^c`$,

the program chooses an exponent u such that

$c\cdot u=1 \bmod p-1$   and   $\gcd(u,q_i-1)=1$,

and replaces $g$ by $g^u$. The first condition gives $`N(g^u)=\zeta`$ and the second
ensures that $g^u$ is still primitive.

Every element of $A^*$ can then be written uniquely as

$x=(g_1^{e_1},...,g_r^{e_r})$.

Because all generators have the same norm,

$`N(x)=\zeta^{e_1+...+e_r}`$,

and therefore

$x\in H$  <=>  $e_1+...+e_r=0 \bmod h$.

For a product of several field factors, one factor is used as a pivot. The
program chooses a factor of smallest degree; if several factors have the same
smallest degree, it takes the first one in the input order. If j is the pivot,
its exponent is represented through a reduced coordinate $y_j$ satisfying

$e_j = h\cdot y_j - \sum_{i \neq j} e_i \bmod n_j$.

Thus $H$ is indexed by mixed-radix coordinates with radix $n_j/h$
for the pivot and radix n_i for every other factor. The pivot digit is given
stride 1, and the remaining factors are appended in their original order. The
integer codes therefore run directly from 0 to |H|-1, where

$`|H|=\frac{2}{p-1}\cdot\prod_i (p^{d_i}-1)`$.

There is no intermediate indexing of the whole unit group $A^*$. Quotients,
inversion, Frobenius, Möbius transformations, and equal-factor permutations are
performed on the exponent tuple and then re-encoded in $H$.

When $A$ is a single field $F_{p^d}$, the description is simpler:

$`H=\langle g^h \rangle`$.

An element of $H$ is represented by one integer k corresponding to

$x=(g^h)^k$,

with $0\le k<|H|$.

From the abstract point of view, $H$ is a finite abelian group and can of course
be decomposed into a product of cyclic groups, for example by a Smith normal
form computation. The program deliberately does not use such a basis. The
factorwise exponent coordinates above make the field automorphisms and
permutations much simpler, while the normalized generators already reduce the
norm condition to one linear congruence.

Frobenius and factor permutations are especially simple in these coordinates.
On factor i, Frobenius sends

$e_i \mapsto p\cdot e_i \bmod n_i$

and leaves the other exponents unchanged; the resulting tuple is then
re-encoded. A permutation of two equal-degree factors simply swaps their two
exponents and re-encodes. Equal-degree factors share the same finite-field model
and normalized primitive generator, so this coordinate swap represents the
actual algebra automorphism literally.

#### 2. Enumeration of the exceptional set

For several field factors, the program precomputes, once for each distinct
factor degree, the table

$L(e)=\log_g(1-g^e)$.

Moreover, the identity $1-(1-x)=x$ is used to fill the table 
in pairs: once $L(e)=f$ is known, $L(f)=e$ is known as well.

After this table has been built, if

$x=(g_1^{e_1},...,g_r^{e_r})$,

then the exponent tuple of 1-x is obtained simply by the lookups

$(L_1(e_1),...,L_r(e_r))$.

The resulting exponent tuple is re-encoded in $H$.

After $E$ has been enumerated, the program also stores, for every exceptional
element $x$, the identifier of $1-x$. Hence the Möbius generator $x->1-x$ used during
orbit classification is only a constant-time table lookup. The logarithm table
therefore speeds up both exceptional-set preparation and the data structures
used for the subsequent orbit computation.

For a single field factor, the program uses a different method. It
enumerates $`H=\langle g^h\rangle`$ directly, tests whether $1-x$ has norm $\pm1$, and computes a
discrete logarithm only for the successful elements.

#### 3. Classification under the global symmetries

The program first builds the images of every exceptional element under a small generating
set:

- $`x\mapsto 1-x`$;
- $`x\mapsto 1/x`$;
- Frobenius $`x_i\mapsto x_i^p`$ independently in every non-prime field factor;
- adjacent transpositions of equal-degree factors.

The first two transformations generate the six Möbius transformations
permuting $`\{0,1,\infty\}`$. Inversion and Frobenius are simple modular operations
on the stored exponents, equal-factor permutations are coordinate swaps, and
$`x\mapsto 1-x`$ uses the precomputed lookup described above.

The exceptional set is then partitioned into symmetry orbits by a breadth-first
search in this generator graph. Each orbit is stored once and a canonical
representative is chosen from it.

#### 4. Canonical local graphs

Consider the i-th global orbit and let o be its canonical representative.
The points 0, 1, and o are now fixed. The remaining candidates are the
exceptional elements x satisfying

$`N(o-x)=\pm1`$

and belonging to orbit i or to a later orbit. Elements from earlier orbits are
excluded because the corresponding normalized cliques have already been
treated.

Since x and o already lie in H, adjacency can be tested without finite-field
arithmetic. The program uses

$N(o-x)=\pm1$  <=>  $`\frac{o}{x}`$ is exceptional.

Thus an edge test reduces to exponent subtraction, mixed-radix re-encoding, and
a bitset lookup in E.

#### 5. Clique number computation

Cliquer is called on the graph induced by these canonical
candidates. Since 0, 1, and o are already fixed, if the internal graph has
clique number c, the corresponding normalized clique has size 3+c.

Different global orbits are independent after preparation, so they are
distributed among worker processes using fork(). The parent process records
every completed orbit and checks that all orbit computations have finished
successfully before reporting the final result.

Optional V4 decomposition:

For a fixed base o, there is a Möbius Klein-four symmetry group preserving 
$`\{0,1,o,\infty\}`$, generated by $`x\mapsto\frac{o}{x}`$ and $`x\mapsto\frac{x-o}{x-1}`$. When V4 mode is 
enabled, the canonical candidate set is partitioned according to its 
intersections with these V4 orbits.

For a candidate x, the program computes its at most four V4 images and keeps
only the images that are themselves present in the current canonical candidate
set. The full V4 orbit does not need to be contained in that set. The nonempty
intersections form a partition of the candidates, and only one representative
from each such class needs to be considered as the next fixed point.

For each V4 suborbit, one representative is fixed in addition to 0, 1, and o.
The associated subproblem then contains only candidates from the current or
later V4 suborbits that are adjacent to this representative. If the internal
subproblem has clique number c, the resulting normalized clique has size 4+c.

The V4 reduction avoids repeated clique searches attached to equivalent choices
of the fourth point, but it also introduces orbit-classification and
subgraph-construction overhead. It is therefore controlled by -v4-threshold and 
remains disabled by default. It is activated on every canonical local graph 
whose number of vertices exceeds the value passed by -v4-threshold.

## Requirements

- a C11 compiler;
- POSIX process and filesystem APIs (`fork`, `wait`, `clock_gettime`, etc.);
- the PARI/GP development library;
- Cliquer 1.21, either installed system-wide or placed in 'vendor/cliquer'.


### Debian or Ubuntu

When the distribution provides both development packages:

```bash
sudo apt install build-essential libpari-dev libcliquer-dev
make USE_SYSTEM_CLIQUER=1
```


### MacOS with Homebrew

Install PARI/GP and build. The Makefile downloads Cliquer automatically when needed:

```bash
brew install pari
make PARI_PREFIX="$(brew --prefix pari)"
```


### Portable vendored build

```bash
make
```

A normal `make` downloads Cliquer 1.21 when it is absent. `make fetch-cliquer` forces a fresh download from its official Aalto University
homepage into `vendor/cliquer`. To use a manually supplied copy instead:

```bash
make CLIQUER_DIR=/path/to/cliquer-1.21
```

To link against an installed Cliquer library:

```bash
make USE_SYSTEM_CLIQUER=1
```

Useful build targets:

```bash
make help
make test
make debug
make sanitize
make clean
```


Timing output uses 9 decimal places by default. Override it globally at build time, for example:

```bash
make TIME_PRECISION=6
```

The smoke tests check both a sequential one-orbit run and a parallel
three-orbit run. They verify the final clique number and the explicit `n/n`
orbit-completion statement.


## Usage

```text
EtaleUpperBound p d1 [d2 ...] [options]
```

Options:

```text
-cpus n           number of worker processes; default 1
-pari MB          PARI stack size in megabytes; default 100
-v4-threshold n   use V4 when the initial local graph has at least n vertices
                  default 0, so V4 is disabled
```

Examples:

```bash
# A = F_(13^5), two workers, direct local searches
./EtaleUpperBound 13 5 -cpus 2

# A = F_(11^2) x F_(11^3) x F_(11^3)
./EtaleUpperBound 11 2 3 3 -cpus 8 -pari 500

# Opt in to V4 for local graphs of at least 4096 vertices
./EtaleUpperBound 11 2 3 3 -cpus 8 -v4-threshold 4096
```

The degree list is ordered only for presentation. Equal-degree factors are
permuted during orbit classification.


## Output

For input `p d1 d2 ...`, results are written in a directory named

```text
p=<p>_d=<d1>x<d2>x.../
```

The directory contains:

```text
result.out          global parameters, orbit results, and final clique number
stderr              diagnostics from the parent and worker processes
local/local_1.out   detailed result for the first external orbit
local/local_2.out   detailed result for the second external orbit
...
```

Old files matching `local_*.out` are removed at the beginning of a new run;
other files in the local directory are preserved.

A typical global orbit line is:

```text
4/27  Vertices: 531  Clique: 8  Best: 9  Time: 0.314159265 s
```

`Vertices` is the number of vertices in the canonical local graph associated with 
that orbit. It counts exactly the exceptional vertices `x` adjacent to the chosen 
base `o`, which is a representative of the orbit. If it exceeds `-v4-threshold`, the V4 mode is activated. 

Parallel workers finish out of order, so the orbit lines in `result.out` are
not necessarily sorted. The parent process maintains a separate completion
bitmap, rejects duplicate completions, validates every local result file, and
refuses to report a complete run unless every orbit was accounted for exactly
once. 

A successful file ends with, for example:

```text
Orbit computations: 27/27 successfully completed
Clique number: 10
Total time: 42.123456789 s
Status: complete
```

A local result contains:

```text
Clique: 9
Time: 0.314159123 s
Orbit: 4/27
Method: direct
Vertices: 531
Best: 9
Status: complete
```

`Best` is the global best clique known to the parent when that orbit result was
processed. In a parallel run it therefore follows worker completion order.
`Status: complete` is appended only after the parent has parsed and recorded the
worker result.

With V4 enabled, a local result additionally reports the number of suborbits
and one line per retained subproblem:

```text
Clique: 10
Time: 3.284271828 s
Orbit: 4/27
Method: V4
Vertices: 4812
Suborbits: 1076

Suborbit 1/1076: Vertices=703  clique=9  time=0.021314159 s
Suborbit 2/1076: Vertices=4  skipped  time=0.000001473 s
...
Best: 10
Status: complete
```

`Suborbits` counts the nonempty intersections of full V4 orbits with the
canonical candidate set; these intersections can have one, two, or four
vertices.

`skipped` means that the subproblem's cardinality bound cannot improve the best
clique already found in that local computation.

All elapsed times use a single build-time precision setting. The default is nine
decimal places so short V4 subproblems are not rounded to `0.000000 s`. For
example, `make TIME_PRECISION=6` selects six decimal places everywhere. This
controls printed precision; the actual clock resolution remains platform-dependent.


### Monitoring a running local computation

Local files are also designed to be useful while an orbit computation is still
running. Once the canonical local graph has been constructed, the worker flushes
all information that is already known **before calling Cliquer**. A direct
computation therefore shows, for example:

```text
Status: running
Orbit: 4/27
Method: direct
Vertices: 531
```

In V4 mode, `Suborbits` is written as soon as the V4 classification is complete,
still before the first clique search. Immediately before each non-skipped V4
subproblem is sent to Cliquer, its size is flushed as well:

```text
Status: running
Orbit: 4/27
Method: V4
Vertices: 4812
Suborbits: 1076

Suborbit 1/1076: Vertices=703  running
```

The `running` line is overwritten in place when Cliquer returns, so a V4 suborbit 
always occupies exactly one line in the live file. Skipped subproblems are written 
directly in their final form. When the whole local computation finishes, the worker 
rewrites the file in the compact final format shown above; the parent then appends 
`Best` and `Status: complete`.


## Performance notes

The dense arrays are indexed by

$|H|=\frac{2}{p-1} \cdot prod_i(p^{d_i}-1)$,

not by the full unit-group size. This reduces the main lookup structures by the
factor $\frac{p-1}{2}$.

The expensive phase is usually the exact maximum-clique search, not algebraic
preparation. Increasing '-cpus' parallelizes independent outer orbits with
separate worker processes. Avoid using more workers than available physical or
logical CPU cores.

V4 can reduce the size of hard clique instances but creates many subproblems and extra 
graph-construction work. It can reduce computation times by a 2-to-10 factor with 
appropriate parameters, in particular for p>=11. A good `v4-threshold` is usually between 
2000 and 10 000. Try using benchmarks to show a benefit for the relevant parameter family. 


### Memory lifetime

Large temporary structures are released as soon as their last consumer has finished.
In particular, the PARI field models and the per-degree `1-x` logarithm tables are
freed before global symmetry-orbit classification begins. During V4 reduction, the
candidate-classification bitset and the canonical candidate array are freed before
the first clique subproblem is launched. Outer-orbit element lists are released
progressively once later local graphs can no longer reference them. In parallel
mode, after the last worker has been forked, the parent releases its complete solver
dataset; the workers keep their inherited read-only copies.

The structures retained throughout clique solving are those needed by future edge
tests and transformations: the exceptional-unit membership bitset, exceptional
exponent tuples, factor metadata, remaining orbit lists, and, when V4 is enabled,
the code-to-ID and `1-x` lookup tables.

## Limits

- The mixed-radix index of `H` must fit in `uint64_t` and addressable memory.
- Cliquer uses an `int` vertex count, so the exceptional set must fit in that
  range.
- The current parallel implementation relies on `fork`, and therefore targets
  macOS, Linux, and other POSIX systems rather than native Windows.
- Each worker writes to the common `stderr` file; simultaneous diagnostics may
  interleave.
